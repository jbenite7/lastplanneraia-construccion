# Facts

- El Sprint 00 entrega un núcleo global versionado, un laboratorio visual, gates automáticos, manifiestos contractuales y una integración piloto en Programa General; no migra toda la aplicación.
- El Sprint 00 continúa desde el estado actual: no se reinicia, no crea otro Epic y no rehace PR 0–2 ni trabajo ya validado; los ajustes pendientes endurecen el contrato de cierre, no reabren la arquitectura.
- El contrato activo de `goal.md`, `facts.md` y `plan.md` prevalece sobre entrevistas y resultados históricos; en particular, ninguna respuesta anterior autoriza forzar commits, usar worktrees, ramas, stash, reset o movimientos Git para aislar trabajo preexistente sin una maniobra posterior aprobada.
- Antes de cada fase, el agente principal consulta el catálogo efectivo del runtime y elige la combinación mínima de skills, plugins, MCPs, conectores, hooks y subagentes que aporte evidencia, calidad, velocidad o seguridad material; una capacidad instalada no se usa por defecto.
- Cada fase registra la capacidad seleccionada, su motivo, acción, evidencia esperada y permiso o riesgo añadido; la mera invocación de una capacidad no cuenta como cumplimiento.
- Las capacidades se enrutan por necesidad: búsqueda local y lectura estructurada para contratos e inventario; skill especializada para decisiones de arquitectura, UI o documentación; Browser/Chrome y Playwright para comportamiento visible y regresión reproducible; plugin, API o MCP oficial para servicios externos; revisión local para el diff de cierre; y conectores de artefactos solo cuando el formato lo exige.
- Skills, plugins, MCPs, conectores, hooks y subagentes no amplían alcance, permisos, autorización para publicar o desplegar, acceso a secretos ni autorización para enviar diffs o datos privados a servicios externos.
- Los hooks son controles acumulativos que se atienden en la fuente y cliente exactos; no se simulan, deshabilitan ni usan para eludir gates o aprobaciones.
- Solo se delegan subtareas independientes que reduzcan materialmente el tiempo total; cada subagente recibe alcance, rutas permitidas, criterio de salida, pruebas y prohibiciones, y el agente principal integra y verifica el resultado.
- Cuando una capacidad requerida no esté disponible, falle o exija una autorización no concedida, el agente conserva el diagnóstico, usa el fallback más seguro, declara la cobertura perdida y no afirma que la capacidad fue usada.
- Toda capacidad seleccionada deja un artefacto verificable proporcional al riesgo: rutas y hallazgos para investigación, pruebas y evidencia de navegador para UI, reportes de contrato para gates, o respuesta/estado verificable para integraciones. La mera invocación no cuenta como cumplimiento.
- No se inicia, continúa ni perfecciona ningún sprint visual por módulo para satisfacer el prerrequisito Git; los cambios pendientes se preservan y aíslan sin mezclarlos con la fundación.
- Antes de implementar el Sprint 00, el staged, los cambios unstaged, los untracked y los commits locales se inventarían y preservan exactamente; cualquier commit, archivo externo verificable, restauración o movimiento usado para aislarlos requiere una maniobra explícitamente aprobada.
- El Sprint 00 empieza sobre el main local solo después de obtener una base limpia mediante el mecanismo aprobado; no obliga a commitear trabajo incompleto, riesgoso, scratch o no aprobado, ni a revisar visualmente sus módulos.
- El Sprint 00 no despliega a producción, no cambia la arquitectura de base de datos, no reescribe lógica de negocio y no introduce un framework nuevo.
- Los tokens actuales y los precedentes visuales ya aprobados en el runtime son la autoridad inicial; Stitch y la documentación de marca son insumos auxiliares, no un mandato de rediseño total.
- Cuando dos precedentes aprobados discrepan, las variantes se comparan y aprueban por familia en el laboratorio; después solo se valida su consumo en Programa General, sin recorrer otros módulos.
- Toda la CSS propia usa una única jerarquía de cascada: reset, vendor, theme, base, layout, components, utilities, module y legacy-overrides; la precedencia de utilities y module queda documentada y probada, y toda regla en legacy-overrides requiere un ID de excepción vigente.
- Los estilos compartidos se cargan en un orden determinista desde un entrypoint global y no se inyectan mediante JavaScript ni mediante bloques style dinámicos de alta especificidad.
- El código propio nuevo o migrado no puede declarar CSS fuera de las capas registradas.
- La CSS de un módulo migrado puede definir composición, distribución, orden responsive y anchos de dominio, pero no puede redefinir primitivas visuales compartidas.
- Los módulos migrados consumen únicamente tokens semánticos para superficies, texto, bordes, acciones, estados, espacio, forma y movimiento; los tokens crudos de marca quedan reservados al núcleo y a adaptadores aprobados.
- Dark y linen remapean la misma API de tokens semánticos y data-aia-theme es la fuente de verdad del tema persistido.
- Ningún componente canónico mezcla superficies, textos, bordes o controles de dark y linen después de cambiar tema, recargar o navegar.
- El núcleo ofrece un puente de compatibilidad para markup y aliases legacy, pero bloquea cualquier uso nuevo de esos aliases desde el Sprint 00.
- Cada alias legacy queda marcado como deprecado y solo se elimina cuando el inventario y los manifiestos demuestran cero consumidores.
- La API canónica combina clases CSS, componentes o partials PHP para markup repetido y módulos JavaScript centrales para comportamiento accesible.
- Cada ficha declara madurez `stable`, `candidate`, `compatibility` o `deprecated`, separada de su aprobación visual: `stable` exige laboratorio, consumidor real y necesidad reusable inventariada; `candidate` puede estar aprobada en laboratorio sin consumidor migrado.
- La garantía SemVer `1.0.0` cubre exclusivamente las APIs `stable`; fichas `candidate`, primitivas BI y adaptadores sin consumidor real quedan explícitamente fuera de compatibilidad estable hasta reunir evidencia.
- El catálogo inicial cubre shell, navbar, drawers, headers, secciones, toolbars, botones, iconos, grupos de acciones, formularios, búsqueda, filtros y paginación.
- El catálogo inicial cubre chips, alertas, carga, error, vacío, cards, tablas, Handsontable, modales, menús, popovers, confirmaciones, toasts, progreso y regiones vivas.
- El catálogo inicial incluye primitivas para gráficas, leyendas, tooltips, estados y contenedores BI dentro del laboratorio, sin migrar rutas ni dashboards BI.
- El inventario del Sprint 00 usa toda la aplicación como fuente de evidencia y debe mapear cada grupo reusable a una API canónica o adaptador, temas dark/linen y espécimen de laboratorio; consultar un módulo no autoriza modificarlo ni migrarlo.
- El inventario incluye explícitamente marca, navbar, hamburguesa, contexto, breadcrumb, drawer, sidebar, usuario, avisos, botones, iconos, formularios, calendarios, selects, filtros, estados, modales, vendors y presentación de datos.
- La familia BI incluye tarjeta analítica, Curva S, barras PPC, comparación PAC vs Programado, gauge, leyenda, proyección, guía por datos insuficientes, resumen KPI, tooltip y tabla equivalente.
- La primera versión inventaría adaptadores para Bootstrap, Handsontable, DataTables, Select2, Tom Select, SweetAlert2, Toastr y AnyChart con madurez `stable-adapter`, `candidate-adapter`, `compatibility-skin` o `deprecated-adapter`; jQuery UI queda como compatibilidad legacy.
- El Sprint 00 no actualiza versiones ni sustituye las librerías de terceros existentes.
- El contrato responsive usa cuatro bandas de viewport para gobernar shell, navegación y evidencia: mobile menor de 768 px, tablet de 768 a 1199 px, desktop de 1200 a 1439 px y wide desde 1440 px.
- Cards, toolbars, filtros, grupos de acciones, tablas/tarjetas y overlays reusables responden al ancho disponible mediante container queries o fallback probado; un viewport ancho no implica un contenedor ancho.
- La evidencia mínima obligatoria se obtiene en 390x844, 1180x820 y 1440x900 para dark y linen.
- El sistema ofrece únicamente dos densidades registradas: compacta para tablas y grillas de escritorio, y táctil para móvil, formularios y acciones.
- El laboratorio es una ruta interna del runtime real disponible solo en desarrollo y pruebas, protegida por entorno y capability `internal.design-system.view`, y no queda disponible en producción.
- El laboratorio presenta todos los componentes canónicos en dark y linen, en las cuatro bandas responsive y en sus estados normal, hover, focus, disabled, loading, empty y error cuando apliquen.
- Los componentes canónicos pasan la matriz automática definida en especímenes controlados y Programa General pasa la matriz del piloto; el Sprint 00 no hace una afirmación integral sobre toda la aplicación.
- La política AIA exige targets de al menos 44x44 px en densidad Touch; en Compacta exige al menos 24x24 px o separación/excepción equivalente permitida por WCAG 2.2 AA. Conservar 44x44 en Compacta es una decisión de producto, no una obligación AA.
- Foco visible, nombres accesibles, regiones vivas, reduced motion y padding semántico son bloqueantes en el alcance evaluado; lenguaje natural envuelve entre palabras, mientras identificadores, rutas, correos, URLs y nombres de archivo usan delimitadores seguros u overflow explícito.
- Playwright es el único runner E2E; `@axe-core/playwright` comparte helper, tags, fingerprints y reportes JSON para laboratorio y Programa General. Accessibility Insights aporta tres revisiones automatizadas básicas separadas —laboratorio, piloto y estados revelados—, cada una con cero reglas fallidas y cero instancias fallidas. Teclado y reflow son evidencia no bloqueante; la evidencia visible y la aprobación estética usan el navegador nativo de Codex.
- La regresión visual automática es bloqueante para los estados deterministas del laboratorio; durante Sprint 00 la única revisión estética de consumo es Programa General, y los demás módulos aplicarán automatización basada en riesgo y revisión nativa en sus migraciones posteriores.
- El contrato registra versión mínima soportada de Chrome/Edge, versión Chromium fijada en CI, features CSS requeridas y fallback. Safari y Firefox se validan posteriormente según riesgo.
- El auditor detecta valores visuales fuera de tokens, CSS sin capa, important no autorizado, spacing, tipografía, sombras y radios fuera de escala, selectores globales de módulo, overrides vendor locales y componentes duplicados.
- Los gates bloquean toda deuda visual o accesible nueva desde el Sprint 00, aunque la deuda legacy global todavía no sea cero; axe solo cubre el laboratorio y Programa General durante este sprint.
- Cada excepción visual o WCAG declara superficie, regla, impacto, archivo o selector exacto, responsable, razón, milestone y fecha de expiración; una excepción vencida hace fallar el gate.
- Los baselines visual y axe están separados y no pueden regenerarse automáticamente para ocultar violaciones nuevas o ampliar una excepción sin aprobación explícita; no se permiten exclusiones generales ni reglas axe desactivadas sin contrato.
- Existe un schema machine-readable para manifiestos de módulo con versión del design system, rutas, componentes consumidos, layouts permitidos, estados críticos, roles, excepciones y cobertura.
- Todo manifest, schema, baseline o contrato declara qué fallo evita, qué proceso lo consume automáticamente y cómo falla si queda desactualizado; un artefacto sin consumidor verificable no entra al núcleo estable.
- Sprint 00 entrega el manifiesto completo de Programa General y un inventario base para los módulos restantes; cada módulo completa su manifiesto durante su migración posterior.
- El design system usa SemVer: permanece en 0.x durante construcción y publica `1.0.0` únicamente para el subconjunto `stable`; el resto conserva su etiqueta de madurez y no recibe garantías implícitas.
- Los cambios `patch` compatibles pasan gates y changelog; los `minor` compatibles agregan revisión visual acotada; los `major` requieren ADR, aprobación explícita y plan de migración.
- Un cambio del núcleo ejecuta el laboratorio y smokes de todos los consumidores afectados; un cambio exclusivo de módulo ejecuta su contrato y los gates compartidos aplicables.
- Los quince gates locales, en su orden contractual, son `static`, `runtime`, `runtime-budgets`, `phpstan-scoped`, `phpstan-global`, `global-table-safety`, `pg-roles`, `pg-persistence`, `data-restoration`, `accessibility-insights`, `consolidated-lab`, `consolidated-pilot`, `git-preservation`, `review` y `atomic-commit`. El workflow de GitHub queda definido y reproducible localmente, pero no se denomina enforcement remoto bloqueante hasta activar required checks mediante `DS-GOV-001`, después del primer push autorizado de `1.0.0`; los hooks locales son auxiliares.
- Cada recibo `passed` usa el `commandId` y el comando exactos del registro canónico del gate; texto libre, incluso si es no vacío, no constituye evidencia. La activación `1.0.0` exige índice y worktree limpios, y que `closeout-evidence.json`, `version.json` y `stable-api-1.0.0.json` coincidan byte por byte con `HEAD`; ese commit contiene la activación completa. El `sourceRef` de los artefactos puede seguir apuntando al commit candidato verificado.
- La configuración externa de branch protection y PR obligatorio para main no se activa durante el Sprint 00; queda preparada y requiere una aprobación explícita separada.
- Git versiona contratos, manifests, métricas y golden screenshots deterministas del laboratorio, además de la evidencia esencial aprobada del piloto.
- Los videos y las capturas extensivas de ejecución se conservan como artefactos y no se agregan al repositorio salvo aprobación explícita.
- El piloto integra exclusivamente la ruta /programa-general; /programa-general-actualizar y las rutas BI quedan fuera salvo smokes o adaptadores compartidos indispensables.
- El piloto conserva comportamiento, datos, rutas y flujos aprobados de Programa General y solo permite normalizaciones visuales hacia componentes previamente aprobados en el laboratorio.
- Programa General demuestra consumo real del núcleo en cards móviles, Handsontable, filtros, acciones y temas sin crear primitivas visuales locales nuevas.
- El piloto verifica dark y linen en los tres viewports obligatorios, ausencia de overflow horizontal, consola limpia, axe, revisiones automatizadas básicas separadas, persistencia, recarga y restauración exacta de cualquier dato de prueba. Teclado y reflow se conservan como evidencia no bloqueante.
- El contrato de trabajo futuro se divide en gobierno global del design system, migración acotada por módulo y revisión/cierre del sprint.
- Una vía `Emergency UI Fix Lane` permite corregir defectos productivos, accesibles, de seguridad u operación durante la congelación; no crea primitivas, no rediseña módulos y toda excepción temporal tiene alcance y expiración.
- Después del Sprint 00 se retoma PDC bajo el núcleo, luego se registran los módulos ya auditados sin reabrirlos salvo fallo objetivo, se migran los módulos pendientes y BI runtime permanece al final.
- El Sprint 00 no exige deuda legacy global cero ni reabre, corrige o perfecciona módulos consumidores; cualquier feedback observado allí se convierte en contrato de familia para el laboratorio y solo se prueba después en Programa General.
- El Sprint 00 solo queda listo para aprobación cuando núcleo, cascada, catálogo, laboratorio, adaptadores, schema, manifiesto piloto, auditor, workflow, documentación y Programa General pasan sus gates.
- El cierre usa `0.3.3` como baseline aprobado para tamaño gzip CSS/JS, adaptadores cargados, requests duplicadas, flash de tema, inicialización, interacción de Handsontable y ausencia de assets del laboratorio en rutas productivas; cada tolerancia está explícita y vinculada a la aprobación del usuario.
- La retrospectiva histórica `0.3.3` es portable pero incompleta: declara `sourceRef:null` y `rawSamplesPreserved:false`, conserva resúmenes recuperados —no las muestras crudas ni sus recibos— y los verifica mediante un manifiesto comprometido. No depende de un objeto o checkpoint Git oculto y no puede presentarse como evidencia runtime actual.
- El gate `runtime-budgets` permanece pendiente hasta recolectar exactamente tres muestras frescas sobre un `HEAD` limpio, conservar sus recibos y agregar sus medianas antes de compararlas con el baseline aprobado. Cero flash de tema y cero assets de laboratorio son invariantes absolutas del comparador.
- PDC medirá después tiempo de migración, porcentaje resuelto con APIs existentes, variantes nuevas, literales visuales, archivos tocados por token, duración CI, falsos positivos y edad de excepciones; esas métricas prueban retorno sin convertir PDC en piloto del Sprint 00.
- El usuario revisa y aprueba la entrega consolidada del laboratorio y del piloto antes de preparar el commit del Sprint 00.
- La familia Acciones queda aprobada con el grupo integrado al canvas: acción primaria sólida, secundaria delineada y estados loading/disabled explícitos; una barra sobre superficie no es la variante canónica por defecto.
- La familia Formularios y filtros queda aprobada con criterios siempre visibles en todos los anchos; móvil apila los campos sin ocultarlos y las acciones reutilizan el grupo canónico.
- La familia Estados y retroalimentación usa fondos semánticos tenues como patrón general, roles status/alert según urgencia y etiquetas completas que nunca fragmentan palabras.
- La familia Presentación de datos renderiza una misma colección como tabla compacta desde 1200 px y tarjetas Touch en anchos menores, sin duplicar lógica ni contenido.
- La familia Capas y diálogos conserva una sola instancia semántica: modal desde 1200 px y drawer inferior Touch en anchos menores, con foco nativo, Escape y retorno al disparador.
- La familia Adaptadores de terceros conserva versiones inventariadas y centraliza skins tokenizadas para Handsontable, Select2/Tom Select y SweetAlert2; los módulos no agregan skins ni estilos inline.
- La familia Elementos de analítica exige figura semántica con título, resumen, leyenda textual y tabla equivalente; el color nunca es el único significado y el Sprint 00 no migra BI runtime.
- Los tipos concretos de chart —incluida la dona actual— permanecen `candidate/analytics-guideline` hasta validarse en un dashboard real; el núcleo sí estabiliza contenedor, tipografía, color semántico, leyenda, tooltip, vacío, tabla equivalente y accesibilidad.
- Estados y retroalimentación separan dos ejes: `lifecycle-state` conserva qué ocurre en el dominio y `severity` expresa cuánta atención exige; info/success/warning/critical son tonos visuales, no reemplazos del estado de negocio.
- `state-semantics.json` inventaría todas las etiquetas por módulo y permite tantos estados de dominio como existan; cada uno mapea gravedad, urgencia, severidad y texto de acción sin renombrar el estado consumidor.
- Icono, búsqueda, paginación, progreso, región viva, menú y popover son APIs ejecutables del núcleo con escaping, validación y comportamiento accesible; ningún módulo define variantes locales durante el Sprint 00.
- Todo escenario determinista declarado en el manifest tiene golden; la cuenta inicial esperada es 60 y puede crecer cuando se agregue un escenario legítimo sin convertir el número en una verdad inmutable. CI compara los archivos y no puede regenerarlos.
- El runtime CI usa puertos y volumen propios, una base mínima sanitizada y ningún dump productivo; al finalizar elimina su volumen sin afectar Docker local.
- El milestone Sprint 00 se entrega como serie revisable de commits coherentes —contratos/auditor, núcleo, laboratorio/goldens, CI, piloto y release—; cada commit es atómico y el staging selectivo excluye todo cambio ajeno. No se reescribe a ciegas el historial ya existente.
- Programa General cuenta con seis goldens deterministas y sanitizados en dark y linen para 390x844, 1180x820 y 1440x900, además de axe bloqueante sobre la misma matriz.
- La leyenda del piloto contiene y envuelve sus estados sin recortar ni fragmentar palabras; la regla pertenece a la familia transversal y no a un parche de vista.
- El fixture CI mínimo tiene schema versionado e IDs deterministas, autentica roles de prueba y sirve Programa General sin datos productivos; aborta fuera de `APP_ENV=testing`, valida una base allowlisted y rechaza cualquier volumen local o productivo.
- Los contratos futuros de gobierno, migración por módulo y revisión/cierre son documentos versionados con pruebas ejecutables bloqueantes.
